🛠️ Ejercicio: "TechStore Inventory API"
Vas a crear una API para gestionar productos tecnológicos.

1. El Modelo de Datos (Base de Datos / JSON)
Cada Producto debe tener:

id: UUID (en JSON) o INT Auto-increment (en SQL).

name: String (ej: "Logitech MX Master 3").

brand: String (ej: "Logitech").

price: Decimal/Float (ej: 99.99).

stock: Integer (ej: 15).

Categorías: Un producto puede pertenecer a varias categorías (ej: ['perifericos', 'oficina', 'bluetooth']).

2. Estructura del Proyecto (MVC Obligatorio)
Tu carpeta debe verse así:

/controllers/products.js

/models/[mysql o local-file-system]/product.js

/routes/products.js

/schemas/products.js (Validación con Zod)

app.js

3. Los Endpoints a Implementar
GET /products:

Debe permitir filtrar por brand (Marca).

Debe permitir filtrar por category (esto te obligará a practicar el JOIN o el filtrado de arrays).

POST /products: Crea un producto nuevo con sus categorías.

DELETE /products/:id: Elimina el producto y sus relaciones (usa la Transacción o el ON DELETE CASCADE que comentamos).

PATCH /products/:id: Actualización parcial. Si se envía el array de categorías, aplica la técnica de "Borrar y Reemplazar".

4. Autenticación, JWT y OAuth2

1. Preparación de la Base de Datos (Capa de Datos)
Antes de tocar el código, asegúrate de que tu tabla users soporte ambos mundos (Local y OAuth2).

Acción: Ejecuta el ALTER TABLE que comentamos (campos password como NULL, provider y provider_id).

Por qué: Si no lo haces ahora, el modelo de Passport fallará cuando intente insertar un usuario de Google sin contraseña.

2. Actualización del Modelo de Usuario (Capa Model)
Crea o actualiza models/mysql/user.js. Necesitas tres métodos fundamentales:

create(data): Que use bcrypt para hashear la contraseña si el proveedor es 'local'.

findByUsername(username): Para el login tradicional.

findOrCreateOAuth({ provider, providerId, ... }): El método "todo en uno" para Passport.

3. Middlewares de Seguridad (Capa de Lógica)
Crea middlewares/auth.js. Antes de tener las rutas, necesitas las "aduanas".

verifyToken: Este middleware debe intentar leer la cookie access_token.

Tip Pro: Si la validación falla, en lugar de solo mandar un 401 JSON, haz un res.redirect('/login') ya que ahora usas vistas EJS.

extractUser: Un middleware global que si el token es válido, ponga al usuario en res.locals.user para que tus cabeceras de EJS puedan decir "Hola, Juan" en cualquier página.

4. Configuración de Estrategias (Passport & JWT)
Configura Passport en un archivo separado (ej. config/passport.js) e impórtalo en tu app.js.

Acción: Configura la GoogleStrategy. En el callback, usa el método findOrCreateOAuth de tu modelo.

Acción: Define cómo generarás el JWT tras un login exitoso (ya sea local o por Google).

5. Definición de Rutas y Controladores (Capa Controller/Routes)
Divide tus rutas en dos grupos:

auth.js: Contendrá /login, /register, /logout y los callbacks de Google.

gadgets.js: Tus rutas actuales, pero ahora envueltas en tu middleware de protección.

6. Creación de Vistas (Capa View)
Ahora que los controladores ya pueden enviar datos, diseña los .ejs.

login.ejs: Formulario POST a /auth/login y un enlace simple <a> a /auth/google.

protected.ejs: Una vista que muestre los datos de req.user para confirmar que la persistencia funciona.

El "Camino Crítico" de ejecución:
Si quieres probar que todo va bien paso a paso, hazlo en este orden:

Registro Local: Crea un usuario manualmente con un script o un test y comprueba que la contraseña se guarda hasheada en MySQL.

Login Local: Logueate, verifica que se crea la cookie HttpOnly en el navegador.

Protección: Intenta entrar a /protected. Si te echa al login, tu middleware funciona.

OAuth2: Finalmente, configura Google. Al ser el paso más "ruidoso" (configurar credenciales en la consola de Google), es mejor tener todo lo anterior ya funcionando.
